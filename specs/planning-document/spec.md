# Plan document contract

| Field   | Value                                                                                                                 |
| ------- | --------------------------------------------------------------------------------------------------------------------- |
| Status  | Shipped                                                                                                               |
| Package | `@re-cinq/planning-document`                                                                                          |
| ADRs    | [ADR-001](../../adrs/ADR-001-packages-and-ports.md), [ADR-002](../../adrs/ADR-002-yjs-is-truth-json-is-projection.md) |

The plan document is the JSON every consumer of a plan reads: the host application and the planning agent. A plan ends at approval; whatever is built from it afterwards, tickets included, lives outside the plan. A template names the sections a plan starts with but does not close the list: the planning agent may add sections of its own, and it edits the plan as one Markdown file, `plan.md`, that the host writes from the plan and reads back as agent ops. This spec states what the contract guarantees, and each statement links the tests that prove it.

## Blocks

- A plan block accepts only the props its config declares, fills a missing prop with its configured default, and rejects an enum value outside its list ([validated by](../../packages/planning-document/src/blocks/plan-blocks.test.ts#L6), [validated by](../../packages/planning-document/src/blocks/plan-blocks.test.ts#L28), [validated by](../../packages/planning-document/src/blocks/plan-blocks.test.ts#L38), [validated by](../../packages/planning-document/src/blocks/plan-blocks.test.ts#L59), [validated by](../../packages/planning-document/src/blocks/plan-blocks.test.ts#L74), [validated by](../../packages/planning-document/src/blocks/plan-blocks.test.ts#L78), [validated by](../../packages/planning-document/src/blocks/plan-blocks.test.ts#L82), [validated by](../../packages/planning-document/src/blocks/plan-blocks.test.ts#L88)).
- A section heading carries no inline content ([validated by](../../packages/planning-document/src/blocks/plan-blocks.test.ts#L49)).
- Custom plan blocks and prose blocks are told apart by their type ([validated by](../../packages/planning-document/src/blocks/plan-blocks.test.ts#L94), [validated by](../../packages/planning-document/src/blocks/plan-blocks.test.ts#L98), [validated by](../../packages/planning-document/src/blocks/prose-blocks.test.ts#L86), [validated by](../../packages/planning-document/src/blocks/prose-blocks.test.ts#L90), [validated by](../../packages/planning-document/src/blocks/block-json.test.ts#L73)).
- Prose is limited to paragraphs, level 2 and 3 headings, nestable lists, quotes, code and tables; images, video and any other heading level are refused ([validated by](../../packages/planning-document/src/blocks/prose-blocks.test.ts#L6), [validated by](../../packages/planning-document/src/blocks/prose-blocks.test.ts#L26), [validated by](../../packages/planning-document/src/blocks/prose-blocks.test.ts#L38), [validated by](../../packages/planning-document/src/blocks/prose-blocks.test.ts#L48), [validated by](../../packages/planning-document/src/blocks/prose-blocks.test.ts#L58), [validated by](../../packages/planning-document/src/blocks/prose-blocks.test.ts#L68), [validated by](../../packages/planning-document/src/blocks/prose-blocks.test.ts#L74), [validated by](../../packages/planning-document/src/blocks/block-json.test.ts#L42), [validated by](../../packages/planning-document/src/blocks/block-json.test.ts#L49)).
- Any block parses through one entry point that picks the plan or prose schema, and filtering blocks by type keeps document order ([validated by](../../packages/planning-document/src/blocks/block-json.test.ts#L11), [validated by](../../packages/planning-document/src/blocks/block-json.test.ts#L25), [validated by](../../packages/planning-document/src/blocks/block-json.test.ts#L55), [validated by](../../packages/planning-document/src/blocks/block-json.test.ts#L67)).
- Inline content is text nodes and links whose plain text joins in order, with styles defaulting to none ([validated by](../../packages/planning-document/src/blocks/inline-text.test.ts#L10), [validated by](../../packages/planning-document/src/blocks/inline-text.test.ts#L16), [validated by](../../packages/planning-document/src/blocks/inline-text.test.ts#L29), [validated by](../../packages/planning-document/src/blocks/inline-text.test.ts#L35), [validated by](../../packages/planning-document/src/blocks/inline-text.test.ts#L41), [validated by](../../packages/planning-document/src/blocks/inline-text.test.ts#L45), [validated by](../../packages/planning-document/src/blocks/inline-text.test.ts#L53), [validated by](../../packages/planning-document/src/blocks/inline-text.test.ts#L59)).

## Metadata and entities

- Plan metadata names an owner/repo, one of five plan kinds, schema version 1, and an optional approval that points at the version it approved ([validated by](../../packages/planning-document/src/plan/plan-meta.test.ts#L20), [validated by](../../packages/planning-document/src/plan/plan-meta.test.ts#L24), [validated by](../../packages/planning-document/src/plan/plan-meta.test.ts#L41), [validated by](../../packages/planning-document/src/plan/plan-meta.test.ts#L47), [validated by](../../packages/planning-document/src/plan/plan-meta.test.ts#L53)).

## Templates

- Each plan kind has an ordered template: a feature runs from intent to open questions, and an incident response starts with what happened ([validated by](../../packages/planning-document/src/template/templates.test.ts#L17), [validated by](../../packages/planning-document/src/template/templates.test.ts#L30)).
- A refactor plan adds a risk section ([validated by](../../packages/planning-document/src/template/templates.test.ts#L34)).
- A UI change always needs a prototype of at least click-dummy maturity ([validated by](../../packages/planning-document/src/template/templates.test.ts#L38)).
- Every template asks for at least one KPI, and no template repeats a section ([validated by](../../packages/planning-document/src/template/templates.test.ts#L45), [validated by](../../packages/planning-document/src/template/templates.test.ts#L54)).
- Looking up a section a template does not have throws UnknownSlotError, and the strict lookup knows no section the agent added ([validated by](../../packages/planning-document/src/template/templates.test.ts#L64), [validated by](../../packages/planning-document/src/template/templates.test.ts#L71), [validated by](../../packages/planning-document/src/template/templates.test.ts#L77)).

## Open sections

- The planning agent, never a person in the editor, may add a section to one plan and rename the sections it added; the template's own sections keep their titles ([validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L179), [validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L221), [validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L236)).
- A section the agent adds has a slot of its own, minted fresh and starting with `custom-` ([validated by](../../packages/planning-document/src/template/templates.test.ts#L121)).
- Resolving a section gives the template's slot when there is one, whatever title the caller passes, so a template's own title wins ([validated by](../../packages/planning-document/src/template/templates.test.ts#L85)).
- A `custom-` section resolves to an optional slot under the title its heading carries, taking prose and the conversation (questions, answers and comments) and requiring nothing ([validated by](../../packages/planning-document/src/template/templates.test.ts#L91)).
- Any other slot the template lacks still throws UnknownSlotError ([validated by](../../packages/planning-document/src/template/templates.test.ts#L113)).
- A plan carrying a section the agent added still passes at approval: the section is not unknown, it breaks no template order, and it is never required ([validated by](../../packages/planning-document/src/validation/validate-plan.test.ts#L134)).
- A block the agent's section does not take, such as a KPI, is reported like any disallowed block ([validated by](../../packages/planning-document/src/validation/validate-plan.test.ts#L149)).

## Agent edits

- The agent writes a section's prose without touching the plan blocks that live in it, and can append to what is already there ([validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L54), [validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L68), [validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L81)).
- A KPI and a prototype declaration are written by id, so sending one twice updates it instead of adding a second, and a KPI people made in the editor is found by its kpiId ([validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L91), [validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L111), [validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L128), [validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L140)).
- A rewritten KPI keeps its block id, so a person working in it keeps their cursor ([validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L158), [validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L128)).
- `add-section` places the agent's section, with its heading, panel, actions and paragraphs, right after the section it names ([validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L179), [validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L190)).
- A new section whose slot is taken or whose anchor is missing changes nothing, and one whose slot does not start with `custom-` is refused by the op schema ([validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L205), [validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L213)).
- `set-section-title` renames a section the agent added; a template section keeps its title ([validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L221), [validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L236)).
- A question's suggested answers travel as one prop, encoded so an answer carrying its own comma stays one answer; a plan written before that reads its comma-separated options as it always did ([validated by](../../packages/planning-document/src/blocks/question-options.test.ts#L5), [validated by](../../packages/planning-document/src/blocks/question-options.test.ts#L14), [validated by](../../packages/planning-document/src/blocks/question-options.test.ts#L18)).
- `add-question` asks a question in a section, with why it asks, its kind and its suggested answers, before the section's actions ([validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L299)).
- A block is written on its own: `replace-block` rewrites the block an id names, keeping that id so a person writing in it keeps their place; `insert-blocks` puts new blocks after the block they follow, or at the top of the section when they follow none; `remove-block` drops one ([validated by](../../packages/planning-document/src/ops/block-ops.test.ts#L31), [validated by](../../packages/planning-document/src/ops/block-ops.test.ts#L48), [validated by](../../packages/planning-document/src/ops/block-ops.test.ts#L63), [validated by](../../packages/planning-document/src/ops/block-ops.test.ts#L81), [validated by](../../packages/planning-document/src/ops/block-ops.test.ts#L94)).
- A block op whose block is gone changes nothing: someone deleted it, and the edit was written against a plan that still had it ([validated by](../../packages/planning-document/src/ops/block-ops.test.ts#L107)).
- `set-section-prose` replaces a section's prose with rich blocks, keeping the plan blocks in it: paragraphs, level 3 headings, bullet, numbered and checklist items nesting items of their own, quotes, code with its language, and tables, their text marked bold, italic, code or struck through, with links ([validated by](../../packages/planning-document/src/ops/prose-input.test.ts#L50), [validated by](../../packages/planning-document/src/ops/prose-input.test.ts#L72), [validated by](../../packages/planning-document/src/ops/prose-input.test.ts#L97), [validated by](../../packages/planning-document/src/ops/prose-input.test.ts#L113)).
- Its blocks take ids the slot mints in order, a nested item under its parent's, so the same prose sent twice writes the same blocks; a level 2 heading is refused, since `## ` is a section in `plan.md` ([validated by](../../packages/planning-document/src/ops/prose-input.test.ts#L50), [validated by](../../packages/planning-document/src/ops/prose-input.test.ts#L81), [validated by](../../packages/planning-document/src/ops/prose-input.test.ts#L86)).

## Changes, one paragraph at a time

- What a pass writes is cut into one change per op, each filed under the section it writes — not the section that was asked — and anchored to the block it is about: the block it rewrites or drops, or the one its new blocks follow ([validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L30)).
- A section a pass adds is structure, and structure is the agent's alone, so the pass is split: the added section and everything the pass puts in it — its blocks, questions, a retitle — are written at once, as a draft's ops are, and only the rest is proposed; a pass that adds no section is proposed whole ([validated by](../../packages/planning-document/src/refine/partition-pass.test.ts#L21), [validated by](../../packages/planning-document/src/refine/partition-pass.test.ts#L57)).
- A change carries the hash of THAT block, so one paragraph moving on leaves every other change acceptable; a block the plan no longer holds hashes as nothing ([validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L53), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L98)).
- Each change carries its own id, so accepting one leaves the rest waiting ([validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L73)).
- A change reads as the words it proposes, one line each, for every kind of op: the paragraphs it writes, puts in place or appends; each prose block it writes or inserts, a list item followed by its nested items; a KPI as "metric: baseline → target by deadline", leaving out the parts it lacks; a prototype as "Prototype (maturity): url", without the url when it has none; an added section as its title, then its paragraphs; a retitle as the new title; a question as its question. A change that only drops a paragraph proposes no words, since what goes is the paragraph it hangs under ([validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L203), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L115), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L183), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L171), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L128), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L141), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L215), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L234), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L250), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L264), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L276), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L195), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L292), [validated by](../../packages/planning-document/src/refine/plan-change.test.ts#L311)).

## Refining a section

- A refine works from settled inputs only: answered questions and resolved comment threads, replies included. Unanswered questions and open threads are handed over as talk to leave alone ([validated by](../../packages/planning-document/src/refine/refine-inputs.test.ts#L43), [validated by](../../packages/planning-document/src/refine/refine-inputs.test.ts#L64)).
- The inputs name the questions and threads a proposal uses, and once they are marked used, the next refine does not write them in again ([validated by](../../packages/planning-document/src/refine/refine-inputs.test.ts#L73), [validated by](../../packages/planning-document/src/refine/refine-inputs.test.ts#L81), [validated by](../../packages/planning-document/src/refine/refine-inputs.test.ts#L88)).
- A section's hash covers what a refine would rewrite, so a new comment or answer leaves it alone and a rewritten paragraph changes it ([validated by](../../packages/planning-document/src/refine/section-hash.test.ts#L12), [validated by](../../packages/planning-document/src/refine/section-hash.test.ts#L21), [validated by](../../packages/planning-document/src/refine/section-hash.test.ts#L27), [validated by](../../packages/planning-document/src/refine/section-hash.test.ts#L32)).
- A proposal is asked for against a section hash and carries the agent's ops and the inputs they use ([validated by](../../packages/planning-document/src/refine/refine-proposal.test.ts#L24), [validated by](../../packages/planning-document/src/refine/refine-proposal.test.ts#L58)).
- A refine the agent could not answer is failed: it keeps the ask and carries the reason, so the person sees why and can ask again ([validated by](../../packages/planning-document/src/refine/refine-proposal.test.ts#L38), [validated by](../../packages/planning-document/src/refine/refine-proposal.test.ts#L48)).
- A proposal's ops stay inside its own section; one that reaches another section is refused with ProposalScopeError ([validated by](../../packages/planning-document/src/refine/refine-proposal.test.ts#L66), [validated by](../../packages/planning-document/src/refine/refine-proposal.test.ts#L105)).
- Each op names its section: a question asked in the refined section stays inside it, and a new section or a retitle belongs to the section it names ([validated by](../../packages/planning-document/src/refine/refine-proposal.test.ts#L70), [validated by](../../packages/planning-document/src/refine/refine-proposal.test.ts#L86)).
- A preview shows what accepting would change, line by line, and says when the section changed after the refine was asked for ([validated by](../../packages/planning-document/src/refine/proposal-preview.test.ts#L43), [validated by](../../packages/planning-document/src/refine/proposal-preview.test.ts#L53), [validated by](../../packages/planning-document/src/refine/proposal-preview.test.ts#L60)).

## Markdown

- The host writes `plan.md` before the agent's pass and reads the agent's edits back as ops against the live plan, so the agent works in plain text while the plan keeps its block ids ([validated by](../../packages/planning-document/src/markdown/markdown-to-ops.test.ts#L67), [validated by](../../packages/planning-document/src/markdown/markdown-to-ops.test.ts#L136)).
- What the file changed is read block by block: a paragraph the file rewrote is replaced by its id, the paragraphs it added go in as one insert after the block they follow, and a paragraph it dropped is removed, so a pass moves only what it touched ([validated by](../../packages/planning-document/src/markdown/prose-diff.test.ts#L34), [validated by](../../packages/planning-document/src/markdown/prose-diff.test.ts#L51), [validated by](../../packages/planning-document/src/markdown/prose-diff.test.ts#L76), [validated by](../../packages/planning-document/src/markdown/prose-diff.test.ts#L86), [validated by](../../packages/planning-document/src/markdown/prose-diff.test.ts#L92)).
- Prose the file wrote back as it was is no change at all ([validated by](../../packages/planning-document/src/markdown/prose-diff.test.ts#L24)).
- The file opens with the plan's title as `# `, then each section in document order as a `## ` heading marked `<!-- slot:... -->` ([validated by](../../packages/planning-document/src/markdown/plan-to-markdown.test.ts#L29)).
- A section's heading carries the title its heading block gives, so a template that retitles a section, or a section the agent named, reads as it does in the editor ([validated by](../../packages/planning-document/src/markdown/plan-to-markdown.test.ts#L39), [validated by](../../packages/planning-document/src/markdown/plan-to-markdown.test.ts#L195)).

## Findings

- The agent raises a finding with `add-finding`, giving its section, a stable id, the text, why it matters and a severity of blocker or warning; the block carries that id so a pass that raises it again updates it in place ([validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L252)).
- A finding is allowed in every section, whatever the template says the section takes ([validated by](../../packages/planning-document/src/validation/validate-plan.test.ts#L100)).
- A finding leads its section like a comment does, ahead of what people wrote, so a reviewer meets it first ([validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L273)).
- Raising a finding a person already resolved keeps it resolved: the pass may repeat itself, the person's decision stands ([validated by](../../packages/planning-document/src/ops/apply-ops.test.ts#L286)).
- An unresolved finding keeps the plan from approval: the approval phase reports `unresolved-finding` for it, naming the section and the block, and the plan does not pass; a draft is never held ([validated by](../../packages/planning-document/src/validation/validate-plan.test.ts#L112)).
- In plan.md a finding is a quoted `**Finding**` line with its id and severity, `resolved` once it is, the text, and its why after a dash, so an agent re-reading the plan can report a standing finding by its id ([validated by](../../packages/planning-document/src/markdown/plan-to-markdown.test.ts#L169)).
